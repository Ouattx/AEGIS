Findings and limits

  • Single-core ingest+validate: 27,235 events per CPU-second at 10,000 lines; feature windows 77,383.
  • Sharded x4 (ingest + windows + SENTINEL, wall clock) vs one core doing ingest + windows (CPU time): 10,000 lines 1.82x, 100,000 lines 2.16x, 1,000,000 lines 2.13x (speed-up is limited by the single coordinator, which reads, identifies and routes every record, and by other processes sharing this host).
  • At 1,000,000 lines the configured traffic needs 50,000 events/s; one coordinator handled 22,958 events/s here, so a deployment at that size runs several coordinators fed by collector-side partitioning (Kafka partitions keyed with aegis.scale.kafka_partition_for_line).
  • Feature-window memory dominates at scale: about 1,666 KB per line for a 24 h window (1,666 GB at 1,000,000 lines). The store keeps per-event timestamps for periodicity features; bounding them (reservoirs) in aegis.sentinel.features is the main lever.
  • RESONANCE at 1,000,000 lines (extrapolated (power law fitted on 4 measured line counts [1000, 2500, 5000, 10000])): 6,427 CPU s and 293 GB per hourly run. Detection is not sharded by destination (the permutation null needs every destination of each line), so at this size the population must be split into independent sub-populations (e.g. per region / BNG), each tested on its own.
  • Sharded RESONANCE preparation (10,000 lines, 4 workers) took 6.4 s vs 4.3 s single-node: at this size shipping the frames to worker processes costs more than the join saves; it pays off only when the line shards already hold their data (Kafka / Kubernetes executors), not with the local executor.
  • 1M-line rows process the same event budget as smaller scales over a shorter simulated window; throughput and per-line state lookups are measured with 1M distinct lines, full-day quantities are extrapolated as stated.
